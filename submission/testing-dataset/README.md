# Offerly AI: Testing dataset

This is the data behind the live app at **https://e-commerce-gx9q.onrender.com/** and the bot **t.me/SmartOffersAI_Bot**. Evaluators don't need to upload anything: the data is already loaded. These files let you see what the app works with, and predict what a test should do.

- **All data is synthetic.** It was generated by the project's own reproducible generator (`npm run seed`, seed 42). No real customers, purchases or discounts exist.
- **Exported** read-only from the live MongoDB Atlas database on 27 Oct 2026. Only seeded customer data, offers and rules are included. No Telegram chat IDs, decisions or anything classmates did are in these files.

## Files

| File | Rows | What it contains |
|---|---|---|
| `customers.csv` | 120 | One synthetic shopper per row: profile, behaviour features, segment, and which offers the rules allow right now |
| `customer_events.csv` | 25,956 | Each customer's behaviour history: sessions, product views, cart adds, checkouts, orders, returns, points earned |
| `offers.csv` | 7 | The offers: terms, who can get them, validity dates, budget and limits |
| `business_rules.csv` | 11 | The active rule set (version 1), in plain language and as parameters |
| `shopper_types.csv` | 8 | The 8 shopper types in the Telegram bot, how many customers each has, their segments and the offers they usually qualify for |

The files are UTF-8 CSV and open in Excel or Google Sheets. Amounts are in rupees (₹), percentages are 0–100, and dates are ISO format (UTC).

### Main columns in `customers.csv`

| Column | Meaning |
|---|---|
| `customer_id` | ID shown in the bot and dashboard, e.g. `CUST-0005` |
| `bot_shopper_type` | The button that links a classmate to this kind of customer in the bot |
| `persona` | The behaviour pattern the generator used (ground truth; the AI never sees it) |
| `segment` | Segment computed from behaviour: champion, loyal, promising, new, at_risk, hibernating, price_sensitive, window_shopper |
| `days_since_last_order`, `orders_90d`, `spend_90d_inr`, `avg_order_inr` | Purchase behaviour |
| `churn_risk_pct`, `buy_probability_7d_pct`, `discount_sensitivity_pct` | Scores derived from the history |
| `return_rate_pct`, `cart_abandon_rate_pct`, `open_cart_inr` | Returns, abandoned carts, and the value of an open cart (blank = none) |
| `reward_points`, `expiring_points`, `points_expire_on` | Loyalty points |
| `eligible_offers_now` | Offers the business rules allow for this customer **before they receive any offer**. Claude may choose only from these. `none` = no offer is allowed. |
| `why_others_excluded` | The rules that excluded the other offers |

`eligible_offers_now` was computed at export time with the project's own eligibility code. Over time it can change: offers expire, open carts age, and once a customer receives an offer, the frequency cap and no-stacking rules apply.

## Shopper types and the offers to expect

In Telegram, **Start** shows 8 shopper types. The bot links you to the **next unused customer** of that type (lowest customer ID first) and names it, e.g. "You are now CUST-0012". Look up that ID in `customers.csv`: `eligible_offers_now` lists the offers you can receive. Claude picks one of them and writes the message.

| Bot button | Customers | Offers they usually qualify for |
|---|---|---|
| Loyal big spender | 9 | LOYALPTS200 (200 bonus points) |
| Deal hunter | 14 | FREESHIP, sometimes WINBACK15 |
| Brand-new shopper | 23 | FREESHIP, WELCOME100 (₹100 off), CARTSAVE10 |
| Drifting away | 15 | WINBACK15 (15% off) |
| Long-lost customer | 10 | WINBACK15, or no offer |
| Cart abandoner | 16 | CARTSAVE10 (10% off the cart), FREESHIP |
| Window shopper | 15 | FREESHIP, sometimes CARTSAVE10 |
| Occasional buyer | 18 | FREESHIP, or no offer |

## Test cases

Tests 1–4 need only Telegram. The rest use the dashboard (admin login shared privately). Customer IDs refer to the rows in `customers.csv`.

| # | What to test | How | Expected result |
|---|---|---|---|
| 1 | Personalised offer within the rules | Bot: **Start** → any shopper type → `/offer` | One offer from that customer’s `eligible_offers_now`. The value, minimum order, expiry and code match `offers.csv`; only the wording is personalised. |
| 2 | No stacking | Send `/offer` again while you hold an unused offer | "You already hold an unused offer — see /myoffers". No second offer. |
| 3 | Claim | Tap **Claim**, then `/myoffers` | Reply "🎉 Claimed! (Demo only — no real purchase.)". `/myoffers` lists it, and Dashboard → Campaign results counts the claim. |
| 4 | Opt-out | `/stop`, then `/offer` | No offers are sent. `/start` opts back in. |
| 5 | No eligible offer, no AI call | Dashboard → Customers → **CUST-0005** → **Preview** | "No offer would be approved". The excluded offers are listed with reasons, and Claude is not called. |
| 6 | Return-abuse exclusion | Customers → **CUST-0019** (45% returns) or **CUST-0042** (100%) → Preview | No offer: the "skip customers who return more than 40%" rule blocks all offers |
| 7 | Likely buyers get no discounts | Customers → **CUST-0035** (open cart ₹3,919, 87% likely to buy) → Preview | Only LOYALPTS200 (bonus points). CARTSAVE10 is excluded by the "likely buyer" rule: no discount for someone already 70%+ likely to buy. |
| 8 | Segment targeting | Customers → **CUST-0012** (at risk) → Preview | WINBACK15, the only offer targeted at at-risk / hibernating customers with churn risk ≥ 50% |
| 9 | Open-cart trigger | Customers → **CUST-0014** (open cart) → Preview | CARTSAVE10 or FREESHIP. CARTSAVE10 requires an open cart. |
| 10 | Expired and draft offers are never sent | Offers page: **FESTIVE20** (ended 25 Oct) and **MEGA30** (draft, 30%) | Neither is ever offered. MEGA30 is flagged "Breaks the current business rules" and **Activate** is disabled (30% > 25% cap). |
| 11 | Marketer changes a rule | Business rules → maximum discount **25% → 10%** → Review & save → Preview **CUST-0012** | WINBACK15 (15%) is now excluded, so no offer. **Change it back to 25% afterwards**, because classmates use the live app. |
| 12 | Full audit | Decision log → open any decision | Candidates, Claude’s proposal, validation result, path (Claude or fallback) and delivery result |

## Recreating the data

Running `npm --prefix server run seed` against an empty database generates a dataset with the same structure, the same 120 customer IDs and the same offers and rules. The generator's randomness depends on the date the seed is run (festive-season and weekend effects), so individual customers differ from these files unless seeded on the same day. These files describe the live database.
